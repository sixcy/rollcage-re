## Optional contract

Only the separately controlled-race held profile can enable:

```json
{"heldForceInput":{"breakpointId":"native-frame-before","maxHoldMs":20000,"shareContainedRanges":true}}
```

Absent/false retains prior allocation/accounting behavior. The existing controlled settings preparer exposes `{shareContainedRanges:true}`; the CLI accepts an optional final `--share-contained-ranges` after explicit level/quality/skip arguments. Its default output remains byte for byte identical to the retained V3 configuration. The original held-only V2 configuration remains unchanged and rejects enabling sharing without controlled settings.

The mode retains71 snapshots, all64 dispatcher observations,128 MiB pending payload,90-second total limit,20-second hold and one attempt. It changes no `maxRegionBytes`, logical allocation/domain, semantic span or event filter. Dispatcher snapshots retain their original duplicated buffers and conservative byte charges. No cross-snapshot storage is shared, including force pre/post snapshots.

## Physical storage and exact logical rows

All original descriptors, pointer chains, vector headers and VirtualQuery region proofs are resolved first while the same owned debug event stops the target. The planner sorts actual ranges by descending length and original ordinal for ties. The first already declared range fully containing a child supplies its backing; an identical row uses the first deterministic owner. A partially overlapping range gets its own full array and full charge. Adjacent ranges are not merged, gaps are not read and no arbitrary address union is used for accounting.

Each maximal backing is read once through its real owner descriptor into an exact-length byte array. Distinct owners must have distinct actual array identities. Each child stores that array reference, `dataOffset` and its original logical length. Bounds, owner identity and actual allocated byte lengths are checked before claiming physical sharing. A legitimate zero-byte vector retains an empty view and no null dereference. Existing vector-header, guard-read,716-byte context and4-byte thread-environment costs remain separately charged.

All consumers use the segment extent: SHA256, buffered/worker publication, held pre-input publication, ordinary FS publication, force revalidation and independent bank-header parsing. File names, row IDs, addresses, lengths, hashes, root/region/vector metadata and each complete per-row blob remain unchanged. File output is intentionally still duplicated. A force verification copy has exactly the logical row length; it patches only that row's actual overlap with force+74..7f and never mutates or clones an entire larger backing for a child. The12-byte independent bank header is extracted from its segment rather than interpreting the backing array as the header.

The payload limit accounts retained capture byte arrays, as before. Existing bounded temporary verification copies and managed-object overhead are not falsely called retained sharing or an overall process-RSS bound.

## Diagnostics and independent loading

Before reservation or full reads, `held-force-budget` retains both duplicated `logicalSnapshotBytes` and physically planned `preSnapshotBytes`, plus the unchanged per-row footprint list and deterministic backing/view plan. The planned metadata has `physicalBufferIdentityVerified:false`; it is not a claim that storage has already been allocated.

After allocation, each held pre-input/before/after snapshot gets an actual `rangeStorage` proof and a separate `held-force-range-storage` diagnostic before its publication. They contain the actual debug-event identity, backing IDs/addresses/lengths, child owner IDs/offsets/lengths, duplicated/allocated byte counts and verified actual buffer identity flag. The final checker requires three distinct matching diagnostics and recomputes every plan from that snapshot's actual rows. Metadata from one event cannot stand in for another snapshot.

The strict partial loader independently checks the owned process, exact request/trace snapshot identity and actual allocation diagnostic before loading shared input. It reads each owner blob once and returns contained Buffer views. Every child blob still has its actual path, length and SHA256 independently checked through bounded streaming. Child content must also match its owner's segment hash. Distinct owner Buffer views cannot overlap the same underlying ArrayBuffer; disjoint pooled slices remain valid. No missing bytes, null pointees, allocation answer or later initialized output is invented.
