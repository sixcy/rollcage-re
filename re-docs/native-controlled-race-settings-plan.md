# Guarded native race selection inputs

This is a static proposal for a separate optional experiment. No C#, capture profile, runtime source, executable, settings file or original process was changed. It preserves the original frontend launch, session/roster generation, RNG consumption, track loader and body constructors. It does not make repeated trajectories or rosters deterministic.

The useful existing input is configuration byte `+0b`, not the constructed session track byte. Retained `052-menu-exit-assembly.json` proves that native frontend launch `43dfe0` calls selector `43ebd0`, then reads configuration `+0b` at `43e0ca`. Values 1–20 override its selected track by native `MOVZX/DEC` at `43e0d5/43e0d8`. Native code then writes session `+579` at `43e0de`, family `+0e` at `43e0f5` from table `574760`, and local index `+0f` at `43e109` from `57477c`. Setting `+579` alone at race startup would bypass correlated producers and leave an already formatted filename stale.

Quality is configuration byte `+31`: native formatter `43b0e0` chooses `high\lev%d` only for exactly one, otherwise `low\lev%d`, using unsigned session `+579` plus one. The proposal accepts only the ordinary binary settings zero/one and requests LOW=0 / HIGH=1. It does not infer that arbitrary non-one values are valid frontend options. The formatter is called at `43ea99`, after session/roster setup. Startup `47ea40` later calls `4797a0` at `47ebe3` and actual `44c2b0` at `47ebea`; its body-construction loop starts at `47f01a→41dbb0`. Thus both settings can be supplied before the next race's asset load or vehicle construction, while the real producers still execute.

The proposed observation/write site is **`43e0c5` before its original `MOV EAX,[5ecefc]`**, immediately before the override read and after the selector succeeded. It avoids forcing the selector result, modifying a jump/register, or depending on a fixed ASLR base. Both roots are observed through image RVAs `1ecefc` (configuration) and `1ecb1c` (session); their heap pointers are captured, never rebased or guessed. A future profile must be distinct from the held-force startup whitelist and leave existing profiles unchanged.

For the supported natural-demo scope, filter the actual configuration `+14/+15` tuple to `00 0a`: original launch mode zero and selector ten. At this point:

- EBX is the preserved original launch ECX and must be zero; configuration `+14` must agree.
- ECX is the successful selected index copied from EAX at `43e0b6`, in 0–19; before the original `43e0c5` instruction EAX still agrees with ECX.
- Launch entry ESP `G` is current ESP plus 20: the prologue pushes ECX, EBX, EBP, ESI and EDI. The original caller is `[ESP+20]`, expected actual module-relative `43dae8` from `43dae3 CALL43dfe0`.
- `[ESP+16]` is saved incoming EDX, expected ten for the demo selector; `[ESP+24]` is the frontend-selected first stack argument, expected 0–3. Capture it; do not replace that RNG-derived choice.
- Capture actual owned main PID/TID, raw CONTEXT716/CW/MXCSR, roots and a 28-byte local caller/argument span. Record the active menu/latch/main-state context; the retained idle route is menu ID4 with launch latch zero. Wrong scope, caller, roots, bytes or counters aborts this experiment.

The only proposed changed bytes are configuration `+0b` (requested one-based level) and `+31` (requested asset quality). Each has an explicit original-byte guard, and every original/replacement byte must be logged. A fresh configuration default for `+0b` is zero; a profile using that baseline should reject a pre-existing nonzero override rather than silently replace it. Quality should similarly use a declared observed baseline, or an explicit accepted set `{00,01}`; other values fail. All native guards must finish before either write, so a failure cannot leave a partially selected configuration. A future typed guard must compare caller/module-relative words dynamically; hard-coding a heap pointer or an observed ASLR return byte pattern is unsuitable.

Existing `captureWhen` can express the exact two-byte configuration-mode tuple. Existing fixed/global-root `MemoryRange` descriptors can capture the roots, configuration bytes, session/header and caller stack. Existing phase writes can express the two fixed one-byte replacements and byte guards. They do **not** by themselves provide atomic all-guards-before-writes, register/caller/module-relative preconditions or a complete one-shot policy: those are explicit requirements for a future reviewed optional settings policy, not functionality claimed by this plan. No profile has been prepared.

Minimum observations are the hook before any writes, the same call after native track/family/local publication, session construction `43e280`, formatter output, startup `47ea40`, and first completed physical-frame entry. Capture configuration `0..a0` (including input `0b`, quality `31`, mode `14..17` and current selection controls), both root DWORDs, session `0..30` and `54d..61c`, raw source stem `6e6660`, the two track classification tables, and the observed participant roster/count/modes/spawn selectors. The post-publication check must establish `579=level−1` and correct family/local table values; the later formatter/loader checks establish the selected LOW/HIGH stem and actual resource input. Later source/physics checkers still require their ordinary full dependency ranges.

`43e280` remains the genuine roster producer. In the actual demo branch it stores session mode `551=0`, attract/live-AI flag `58c=1`, count `54d=6`, six participant modes8 and original authored spawn indices0–5. Its loop calls `43ddf0` at `43e56e` for unresolved selectors and stores them at `43e579`, bounded by the six-iteration comparison `43e57e`. Do not write the generated `+1c..21` array or frontend RNG to make a convenient roster. Capture the actual selectors and classify each matrix row by them. `41dbb0` consumes `session+1c+index`; `47ea40` reads the count at `47efef` and performs actual constructor calls at `47f01a`. This is a counted native six-car roster, not six assumed identical chassis records.

Difficulty must also remain native. Retained `2345` proves first `410060` sees `session+58c==1` at `4100a5` and writes effective `5ea4d8=2` at `4100b9`. Thus these live demos use Expert even if the session's menu difficulty differs. Original `43dfe0` also clamps session `+585` and gates harder menu choices on unlock bits at `+720`; this proposal does not alter those bits or effective `5ea4d8`. Track-derived AI stage `920f84` must still be produced from the selected track by `410060`. Easy/Hard matrix coverage needs a separately established normal frontend race path and its real settings/input ownership, rather than clearing demo flag1 or overriding difficulty globals.

The retained **closed** `hidden-idle-capture` provides an existing unmodified example: launch snapshot5 has ECX0/EDX10 and actual caller `71dae8` under base `6e0000`; construction snapshot6 has frontend tuple mode0/selector10/argument0 and session track2; startup snapshot8 has `high\lev3`, count6, mode0, attract1, phase1, six modes8 and roster `[6,5,4,3,2,0]`. Before launch its session still contains prior menu/session values (including phase8 and a different roster). Do not require blank bodies/zero phase or overwrite that state; native reinitialization owns it. Those startup snapshots capture config `10..1f`, not `0b` or `31`, so they do not supply an observed original-byte guard for the proposed hook. New early observation must retain those exact fields.

No original command-line or INI key for these two settings is established. Retained parser `441c10` and literal data `026` prove legacy `/PLAYBACK` and `/FRONTEND`. The existing bounded wide-parser audit finds renderer `/device`, `/wireframe`, `/width`, `/height`, `/bpp`, `/novsync`, `/antialias`, `/windowed` and path normalization; that renderer/device state must not be confused with legacy asset-quality byte31. There is no evidence here for `/level`, `/track`, `/low` or `/high`. Default producer `486490` clears the configuration (so byte0b initially zero) and writes DWORD `+30=02000101`, making byte31 one. Calls `4862a0`, `486b30` and `486bb0` appear in startup/configuration flow, but their detailed field-level writer/key schema is not recovered here; their names alone do not establish a file-loading role. Focused future static requests should recover those bodies and exact writers/readers of these configuration fields before preferring an original file/CLI route. `43b0e0` and `43ebd0` also need retained complete assembly for a future instruction-checked profile generator: current selection/formatter contracts use their original pseudocode plus the complete surrounding launch/startup assembly. No settings-file modification is currently justified.

Track selection can stabilize a native track/quality matrix without hiding remaining variability. Preserve and report native roster, time-derived session seed618 and all RNG streams; do not promise identical initial RNG, contacts, collision objects or audio schedule. Exercise every declared racing track/quality rather than selecting only favorable layouts. The viewer's user-requested exclusion of LEV16/17 (no racing paths) remains separate; a racing matrix can enumerate the same 36 LOW/HIGH variants explicitly, while reporting why those two are excluded. Do not claim whole-game or full physics-matrix closure from a settings-only selection experiment.
