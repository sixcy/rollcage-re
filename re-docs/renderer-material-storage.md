# Material copying and property-vector ownership

`src/renderer-material-storage.mjs` reconstructs `50ddb0` material copying, `5149e0` destruction, `4023d0/406580` property deep copies and the complete `404ea0/405250/405560` 40-byte property vector. It calls the actual narrow/wide string implementations and typed-value/destruction helpers. Evidence: retained `13279/13280`, `13281/13282`, `13285/13286`, `13406/13407`, `13408/13409`, `13422/13423`, `13442/13443`, plus the string/value evidence linked from [renderer-material-construction.md](renderer-material-construction.md). Target SHA-256: `c0582271862ec373f00d01545c2a95aef0abb10a32513ec585271d08b10c6cf5`.

The raw APIs accept `{memory,scratchBase,services.libraryCall}` with the actual native entry ESP. `copyRendererMaterialValue(output,input,runtime)` copies the narrow name, clears conversion ownership and independently allocates/copies the type-selected value elements. `copyRendererMaterialValues(first,last,output,runtime)` returns the end of the newly constructed range. `appendRendererMaterialValue(vector,input,runtime)` preserves an aliased element's logical index through growth. `reserveRendererMaterialValues` retains requested capacity while overwriting its caller argument with logical size and reloading that size after destruction/free callbacks. `growRendererMaterialValues` implements the original 1.5x policy and `06666666h` element bound; its reserve call is a native tail call at the same entry ESP.

`copyRendererMaterial(output,input,runtime)` preserves self-assignment as a no-op, then copies the header in native word/byte order, assigns the wide name, copies attributes using the live signed byte count and destroys the destination's existing properties. It constructs each source property through a temporary, appends a deep copy and destroys the temporary's independent owners. Source root/count are reread at their native loop points, including after declared allocator/free mutations. Attribute counts are not artificially clamped to eight. `destroyRendererMaterial` retires property/value/name storage in native order, reloading each later owner after callbacks. A null property root skips the entire vector reset branch, preserving stale end/capacity fields.

`node tools/verify-renderer-material-storage-instructions.mjs` passes **600 fixture worlds, 8,400 entry calls, 872 reached instructions and 3,821,125 steps**, comparing all mapped bytes at and above `10000h`, meaningful return values, ordered genuine CRT calls with exact child ESPs and restored FS linkage. Its seven entry scenarios cover all typed values, heap/SSO property names, populated destination arrays, signed attribute counts, self-assignment, aliased append, allocation-side logical-end changes, post-delete caller-length changes and destructor-side source-count changes. Persistent scenarios execute actual material construction, three property appends, material copying and both material destructors in one shared memory world. No game callee is mocked and no original process is run.

Five focused tests cover independent value ownership, append rebasing, post-delete live length, byte-preserving self-assignment and stale null-root headers. Shader compilation and effect metadata remain separate renderer-startup work.
