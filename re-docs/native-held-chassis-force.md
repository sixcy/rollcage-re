## Preparation and host planner

Root alone announces and starts the original game. The new tools expose these preparation/verification commands:

```text
node tools/prepare-native-held-chassis-force-capture.mjs ISOLATED_ROOT NEW_CAPTURE NEW_CONFIG [SKIP_FRAMES]
node tools/plan-native-held-chassis-force.mjs NEW_CAPTURE --wait
node tools/check-native-held-chassis-force.mjs CAPTURE NEW_REPORT_FILE
```

The planner's optional `--wait` watches for one atomically published request for at most90 seconds, so it can be started before root launches the capture. It launches no process and makes no OS/device/input changes. It loads one request, tries one bounded plan, and publishes at most one decision. There is no automatic resampling, next-frame retry or force fallback. Existing output files are refused; decision publication uses an exclusive hard link after the complete plan and packet are closed.

`heldForceInput: {breakpointId:'native-frame-before', maxHoldMs:20000}` selects a separate one-frame contract: actual4749e0/preRET474b1e, actual474bb0 dispatcher, phase4, six actual participants, matching entry/return skip counts (default120), one candidate frame,70 total snapshots,64 dispatcher snapshots,90-second total duration and128 MiB pending bytes. The pre-input observation, normal post-input before observation, after observation and all dispatcher observations are charged to those limits. Before offering a live request, the helper checks available snapshot space and conservative pre/post/after plus fixed dispatcher byte costs. Newly enlarged after-frame regions can still fail the normal budget; no partial result becomes positive proof.

Independent JS and C# validators allow only the three established launcher/graphics/device policy sites and their six exact startup writes/guards, followed by the three declared frame/dispatcher sites. Added sites, moved startup sites, participant/pose writes, extra actions and weakened startup preimage guards are rejected. The held contract cannot use another phase action to position a car before planning.

JS and C# require the independent header bytes, root, begin/end/capacity, alignment and full storage extent to agree. Null storage is valid only for an all-zero header and grants no mapped memory. Other vector transports remain forbidden by this held policy. The old whole-region descriptor remains accepted solely for inspecting the retained V1 configuration; new preparation emits the exact vector descriptor.

Before any pending-byte reservation or large blob read, the helper now retains `held-force-budget`: the actual resolved per-range addresses, lengths and footprints, including each12-byte vector header cost, context/TLS cost, fixed dispatcher reserve and total required bytes. The result checker recomputes this evidence from the actual request/configuration. A refusal leaves the live footprint breakdown and writes no force. ## Actual held input and guarded write

At the selected owned main-thread entry, the helper proves the original451017 return word and current active phase/participant count. It leaves the original Windows debug event uncontinued. All target threads remain stopped by that event; no peer is resumed for planning. The existing instruction restoration, stepping, rearm, owned-handle and queued-breakpoint rules resume only after the input is checked. Microsoft documents the debug-event freeze in [ResumeThread remarks](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-resumethread).

The actual raw716-byte context and complete declared input ranges are first retained as `held-force-pre-input`, with `observedBreakpointId:'native-frame-before'` and `capturePhase:'held-pre-input-before-original-instruction'`. This logical observation label does not claim a second breakpoint or executed instruction. `held-force-request.json` binds a fresh128-bit token, executable identity, PID/TID/debug ordinal, observed module base and clock, limits and the exact snapshot filenames/hashes. It is published only after all blobs close.

The strict partial loader checks the configured descriptors, actual pointer-slot bytes/root chains, range bounds, hashes, overlapping aliases, registers against raw context, x87/MXCSR metadata, phase, roster, clock/caller and consistent FS descriptor/SEH-head evidence. It supplies no missing heap/TLS bytes. The final result validator additionally requires the actual held debug-event/intervention sequence; loading a synthetic protocol fixture by itself establishes no native runtime observation.

The source planner executes the real unmodified physics as a **source-only counterfactual baseline**, generates current candidate planes from the captured geometry, and tries at most24 force clones. Directions come from genuine type6/7 candidates; at most four distinct directions per participant are enumerated with signed4/16/64 Q16 scalars, stopping at the total trial limit. Every clone preserves all bytes except the selected participant's12-byte force accumulator+74..7f, including pose, quaternion/matrix, momentum, spatial/shape/cache and vehicle state. A forecast qualifies only after complete source execution and an actual selected type3/planned-border event. Misses and unbound/failed trials remain in the plan; a partial event never qualifies. The smallest successful scalar wins, with deterministic enumeration order for ties. Issued forecasts are bound in-process to their original content before a decision can be encoded.

The decision packet is a strict12-line ASCII-compatible protocol: protocol tag, token, exact request SHA256, participant index, body address, complete original3e78-byte body SHA256, original/next12-byte force hex, normal vector, signed scalar, source-plan SHA256 and final empty line. It exposes no arbitrary write address, register/code replacement or output seed. C# independently checks canonical integers/hex, index0..5, nonzero bounded normal/scalar, checked signed force arithmetic and resulting absolute force≤0x01000000.

Before writing, C# re-resolves every root, re-queries captured region ownership/protection, rehashes every captured input span and checks the full stopped context again. It verifies the current participant root, type3 body,128-byte arena alignment/full extent, physical-list membership/terminator, actual registry index/backlink, body hash and force preimage. Only then does it write exactly body+74..7f. Every captured byte is read again against its original value plus that exact overlapping12-byte window; the context must remain unchanged. A successful `held-force-intervention` retains the actual values, identities, hashes and elapsed time. The new actual normal before snapshot is explicitly tagged `heldForceInputPhase:'post-input'` and linked to the pre-input ordinal.

Both the20-second hold deadline and90-second total deadline are checked using the debugger's monotonic clock. A timeout, stale request, changed input, malformed packet, no complete source forecast or failed guard aborts the attempt without retry. No forecast means no decision packet; the source-only plan remains, and the helper terminates at its bounded wait deadline without a force write. A post-write verification failure is retained as a failed observation and the original instruction is not resumed. These are safety/coverage failures, never controlled collision matches.
