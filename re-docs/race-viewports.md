# Race viewport startup

`src/race-viewports.mjs` reconstructs actual `450a90`, with actual game defaults for participant selection `471770`, layout `42ef80`, application construction `403430`, texture/target/viewport creation `404020` and named enabling `406b80`. The public entry is `initializeRaceViewports({memory,scratchBase,entryRegisters,handlers,services})`. The `47ea40` caller uses child entry ESP equal to its own entry minus48. Optional named game overrides remain available for isolated boundary tests; the connected native proof supplies none.

The unconditional selection/layout prefix runs even after creation has already happened. In offline mode `471770` adds the two original four-DWORD tables at `5dcc60/5dcb80`, wrapping each SIMD lane. In network mode it retains the signed local ID `6e9f70`, then takes up to three other exact-status1 peers in ascending index order from six records at `6e7884+i*67c`; unused selections become zero. It does not validate or normalize the local ID. These four selections are written at `5ec120..5ec12c` and feed the actual four-argument `42ef80` ABI: first ECX, second EDX, third/fourth on the stack.

`42ef80` captures the initial session mode at `session+552` for its layout switch, while later border/configuration reads remain live. It writes selected participant rectangles beginning at `909308+i*30c` (participant record+8), projection dimensions, packed globals and duplicated auxiliary colors. Modes0/1/2/3/4 select one view, horizontal pair, vertical pair, three views and four quadrants. Unsupported modes retain the native zero-size arithmetic, including negative extents after borders. Duplicate participant selections overwrite in native order. Only the low WORD of `6f9bfc` is cleared; high bytes remain stale. The separate 10,000-call layout proof includes raw wrapped participant/local aliases and negative IDs; the full startup proof uses valid mapped participant IDs.

`450a90` sets DWORD `6e6758` to1 before creating any view. It repeatedly reads the live stage count through actual `41bef0`, constructs ordinal names (`0 Player`, etc.) but reads rectangles from the selected participant, and rechecks the application singleton around every definition/enable call. CRT RTTI arguments and pending game arguments occupy the real shared stack and are reloaded after RTTI. Mirror dimensions and cinematic dimensions follow the original integer formulas, preserving cinematic X=-10 for zero display width.

The gate's original DWORD is zero (REA13024). Typed incoming references13010 identify only `450ac7` read and `450ad4` write. No reset/destructor producer has been demonstrated; no reset is invented. The original three name literals were first extracted independently from the SHA-verified installed PE and then corroborated by REA13008/13009. Canonical `race-viewport-constants.json` retains those bytes plus the offline selection and stock-name bytes. This does not claim that Ghidra's indexed references enumerate every computed write.

## Actual renderer creation

`createApplicationViewport` in `src/application-viewports.mjs` implements `404020`. It obtains a real texture ID from the actual pool algorithms, applies the live supersampling option, calls actual renderer virtual80, constructs a76-byte named target, registers it through actual `517d70`, constructs a25c-byte scene-linked viewport through actual `50e370`, appends the viewport to the target and publishes the application-map record. Named enable `406b80` captures exact DWORD equality to1 before map insertion; only its byte is written.

The constructor preserves aligned stack addressing, allocation order, the uninitialized/padding bytes of both objects, repeated renderer/singleton reads, native width/height captures, live application+6c, copied rectangles, cookies and string ownership. It does not treat renderer virtual80 or target insertion as external services. See [texture creation](renderer-texture-creation.md) and [target registration](renderer-target-registration.md) for those actual descendants.

The remaining services are genuine CRT allocation/free/SSO storage, `_itoa`, RTTI, atexit and the debugger's platform critical-section calls if bootstrap is needed, plus Direct3D COM allocation/query/release. `services.direct3DCall(object,method,args,runtime)` receives the exact native DWORD stack arguments, including the COM `this` argument as `args[0]`. It must populate output pointers when its HRESULT indicates success. No host graphics device is created or called by these checks.

## Evidence and validation

All evidence uses Redux SHA256 `c0582271862ec373f00d01545c2a95aef0abb10a32513ec585271d08b10c6cf5`. Parent9008/9009 and new13000..13052 cover selection, layout, creation, enabling, stock names, target insertion, resource release and original tables. Existing renderer114xx evidence supplies resource creation policies and vtables. The retained program loader checks target digests and rejects conflicting instruction/table evidence.

- `verify-race-viewport-layout-instructions.mjs`:5,000 fixtures per entry,10,000calls,228 reached instructions,810,556steps.
- `verify-application-viewports-instructions.mjs`:1,000 persistent maps,7,000 enable calls,854 instructions,4,851,003steps, including allocator mutation of the incoming enabled argument.
- `verify-application-viewport-creation-instructions.mjs`:200 worlds,4,000 producer/creation/enable calls,1,800 actual target/viewport creations,2,757 instructions,10,817,888steps. Separate growth report:two worlds with132 views each,532calls,2,808instructions,2,880,951steps, consuming the original128 free texture slots and growing both texture and integer pools.
- `verify-race-viewports-instructions.mjs`:600 worlds,three actual parent calls per world plus1,200 actual texture/integer constructors;3,000 total calls,3,206 reached instructions,20,405,970steps. Includes2,272 actual `404020` calls,181 lazy actual application constructors and1,800 actual selection/layout calls each. Repeated calls prove the gate retains layout updates without recreating views.
-28 focused tests cover the new layout/parent/enable/texture/registration behavior. Parent boundary tests explicitly use named overrides to isolate live counts, singleton re-entry and pending-argument aliases; the full instruction comparison uses actual defaults throughout.

All connected checks compare every mapped byte at or above10000h, ordered CRT/Direct3D requests and restored explicit synthetic FS exception chains. The separate parent-only historical contract proof remains under `tools/next-phase/race-viewports/`; it is superseded for closure by the actual connected report. These are synthetic raw-memory instruction comparisons, not original-process runtime observations.

Caller-owned renderer roots/device capabilities remain an upstream initialization requirement. Existing actual `50f510/514800` manager constructors initialize pools and fields but intentionally do not initialize a graphics device. Full bootstrap `519df0`, initialization `510080`, device capability ownership and renderer-root publication `6e6388/714ae8` require their own connected producer proof. This package closes viewport startup algorithms; it does not establish a complete operational renderer, shutdown or the entire `47ea40` session startup.
