# Physical vertex pools and shared CPU views

`src/renderer-vertex-pools.mjs` implements actual52c9c0 physical pool configuration and52cc70 view attachment. APIs are `configureRendererVertexPool(pool,flags,count,texCount,mode,runtime)` and `attachRendererVertexPool(vertex,flags,count,texCount,usage,pool,runtime)`. Both use shared raw memory/native entry ESP and actual logical-layout/allocation/assertion descendants.

Physical stride includes flag20h's16 bytes, unlike the logical52d380 layout. Mode0 reserves at least256KiB using a signed wrapped size comparison. Pool memory is genuine unzeroed malloc storage; repeated configuration overwrites the backing pointer without inventing an old-block free or refcount reset. Native capacity/free-byte/used fields are written before allocation; malloc-side mutations survive except the final backing-pointer store. Null allocation invokes actual4a1fe0 and can still return AL=1 with a null backing pointer if the assertion continues.

Attachment publishes the pool pointer, snapshots the previous used count and derives the backing address from physical stride. It increments used/refcount and decreases free bytes before actual52d380 configuration. The logical view therefore keeps its own stride and field widths while borrowing the correct physical start. Existing GPU/declaration cache fields are preserved;52cc70 itself does not refresh them. Null backing storage follows the actual logical helper's allocation policy rather than an invented no-op.
