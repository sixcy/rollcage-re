## Completion requirements

The goal concerns reference algorithms and their state, rather than producing C, reproducing original machine code, or implementing Windows/GPU hardware. A module is complete only when all the following are established:

1. Its entry points, caller conditions, state/storage layout, authored data and outgoing calls have been identified for the selected Redux build. Native functions and indirect dispatch targets are assigned to an owned module or explicitly classified as imported/runtime services. Unknown dispatch targets remain open work.
2. Every relevant target-owned numeric operation, state transition, traversal and branch is translated with its fixed widths, signedness, aliasing, ordering and retained-storage behavior. A callback to an unported game routine keeps the containing feature incomplete, even when the caller is verified.
3. Required state producers are recovered or are legitimate external inputs with a documented contract. Keyboard events and a device clock can be external inputs; an unexplained speed field, checkpoint update, AI decision or damage result cannot silently become one for completion purposes.
4. Valid, boundary and reached unusual states are checked against evidence appropriate to the claim. Instruction replay establishes agreement for its retained code and declared callbacks. Asset validation establishes structural/data coverage. Neither proves original-process trajectories, visual equivalence or unobserved caller behavior.
5. The module is connected to its actual callers and consumers, with meaningful scenarios exercising its complete feature paths. A test that supplies the answer at the same boundary does not establish the missing algorithm. Synthetic fixture initial conditions must be distinguished from recovered constructors and captured runtime state.
6. All game-owned callees, data variants and modes within the module are closed, or evidence establishes that an exclusion is irrelevant/unreachable in this build. Original OS, graphics, audio and transport APIs can remain explicit service interfaces, but the game's decisions and transformations around those services must be reconstructed.
7. Research notes identify the supporting native addresses/Evidence IDs, independent checks, remaining limits and ownership. A known unresolved requirement prevents a whole-module completion claim.

Overall completion requires closure across the subsystem table and a final cross-module audit. This includes the surrounding game tick, lifecycle, race/session modes and initialization/teardown paths, not only a driving/collision loop. Source file counts, passing test counts, fixture counts, procedure counts and earlier rough estimates are not a measured denominator.

## Integration and evidence needed for the whole-game claim

The existing eight-frame installed-data probe establishes connected numerical physics under its declared state. The separate post-frame probe establishes route selection, placement, reset and particle creation under its declared mode3 session. The checkpoint probe establishes its supplied progression cases. Their scenario boundaries do not by themselves prove that these stages share one correct race/session runtime or that initialization reaches them with the right values.

The remaining integration audit must start from native initialization and trace a complete relevant tick into input/AI, controls and weapons, physics, attachments, rejection/recovery, progression/results, effects/audio/render submission and persistence/network consumers. It must also cover restart, pause, mode changes and teardown. References can use explicit OS/device/transport interfaces, but every game-owned transformation between those interfaces requires evidence and implementation.

Before a final completion claim, produce a function/module ownership inventory covering known direct/indirect call closure and remaining unidentified regions; reconcile each table row and concrete callback above against current sources and reports; validate authored-data variants and mode branches; and retain a final requirement-by-requirement review. Any unresolved game algorithm or missing producer remains open. A green aggregate suite proves the behavior it checks, not the entire game's reconstruction.
