# Live chassis-border force experiment: feasibility audit

Read-only audit, 2026-10-23. This new analysis note is the only file added. No game launch, implementation/configuration change, REA session, installed-file write, viewer edit or rejected native fixture execution.

## Conclusion

A controlled native comparison is feasible **conditionally on a complete preflight of the current, held native input**. Existing fixed phase actions cannot implement that handshake. They can apply a previously prepared literal only when its full declared preconditions match; clock348, participant1 and the old vector alone are insufficient. The smallest clean extension is a single bounded hold at actual4749e0 entry, followed by one checked12-byte force write and the existing complete-frame/event comparison. A miss, missing dependency, timeout or changed input must end that attempt without trying another live frame automatically.

The preserved old preflight remains useful evidence of source feasibility:24 fully completed source trials,8 chassis-border forecasts,3 contacts on the planned plane; smallest successful planned-plane trial14 uses increment[-245760,0,-999424]. This is conditional on that retained process's inputs. It is not a transferable literal or a native collision result. New startup track, roster, spawn, AI history, allocations and timing may differ.

## What exists now

`MemoryWrite` in `tools/lib/native-physics-debugger.cs` resolves RVA/register pointer chains and checks exact bytes before a fixed replacement. It computes neither normals nor force. Configuration is read before launch; no request/decision or held-resume input channel exists. Validation forbids phase actions at pending-frame observer sites and filtered sites. Action guards are checked one write at a time, so they are not a generic atomic read-only guard transaction. An ordinary snapshot is emitted before actions; trace rows are flushed immediately, but the helper then steps/continues without waiting for a host decision.

The separate unfiltered451012 CALL4749e0 site could perform a completely predeclared action. For a previous-frame literal, its guards would need the actual phase, clock, selected root/body, all relevant pose/orientation/momentum/force/mass and geometry inputs. Pointer-chain resolution avoids stale heap addresses but does not establish those semantic preconditions. No-op phase writes could test some bytes, but would still be writes and would not compute a fresh plan. They should not be used to disguise missing live planning.

Prefer4749e0 itself for a new typed held policy: its return address, entry ESP, raw context and numerical environment are then actual observations. Holding451012 instead would require synthesizing the CALL's pushed451017 return word and decremented ESP for the offline entry. That can be derived from instructions, but is unnecessary here and would complicate private-ABI provenance.

## Proposed optional contract, not implemented

Use a dedicated one-frame profile and a narrow `heldForceInput` policy, separate from generic `phaseActions`. Preserve legacy policies unchanged. Suggested limits: one hold, one affected participant, one12-byte write, at most24 offline attempts/four actual candidate directions per participant, scalar magnitudes4/16/64 Q16 and maximum absolute resulting force0x01000000. A20-second hold deadline must also fit inside the unchanged90-second capture deadline; this is a timeout proposal, not a measured planner-latency guarantee. Retain the existing128 MiB buffered cap and explicitly charge request/post-input snapshots against the declared snapshot budget. No budget bypass or automatic resampling.

1. Admit the actual owned main-thread4749e0 entry after the existing phase4 selection/explicit skip bound. Prove the relocated451017 return word, frame/thread/PID identity and actual clock; do not assume the recovery caller's229 raw hit applies here. Capture the raw716-byte context, thread numerical environment and the existing complete native-frame input ranges. Keep this debug event **uncontinued**, not merely the main thread suspended while peers run.
2. Publish a new immutable held-request manifest and hashed blobs plus a unique request token. The manifest binds executable/configuration hashes, PID/TID, debug ordinal, module base, clock, phase, registers/context hash, every range address/length/hash and its actual root chains. A bounded host tool reads this snapshot, never process memory from another run.
3. Run the real source frame unchanged to generate current candidate geometry, then the bounded force clones through the same complete source physics. Reject unbound/partial forecasts. Derive directions from genuine current type6/7 candidate records and captured vertices/normals/spatial data; use checked signed64 Q16 multiplication/addition, no world-axis assumption or clamp. Pick at most one completely executed type3/planned-border forecast. The decision supplies only the selected participant, original/next force bytes and proof hashes; it must not permit arbitrary addresses, registers, code or output writes.
4. Before any write, validate the complete decision against the held request, re-read every guarded input span/context/root, verify exact equality and re-resolve the selected body from the actual909300+index*30c root. Validate the live type3 body,128-byte arena alignment, complete3e78 extent, registry/physical membership, session count/index and declared force arithmetic. All validation precedes the single write. A stale token, changed byte, unsupported context, miss, invalid pointer or deadline is terminal for this attempt.
5. Write exactly body+74..7f. Preserve actual pose, quaternion/matrix, momenta/velocity, torque, mass/inertia, spatial links, shape/contact/cache/vehicle bytes and all context registers. Retain exact pre-write bytes and re-read them after the write. Publish a separate actual post-input entry snapshot; only that snapshot becomes the normal before-input for source/native frame comparison. The pre-write held observation remains separately identifiable, never relabeled as unmodified input.
6. Resume the existing original-instruction/single-step and breakpoint ownership machinery once. Keep the current pending/redeferral and owned-handle rules. Capture actual dispatcher observations and the complete after frame. On timeout/decline, either terminate cleanly or finish a clearly labeled **unmodified** baseline, with no second selected frame or fallback force.

Windows documents that reporting debug events freezes the reporting process's threads. Consequently retaining the original event before `ContinueDebugEvent` is a suitable hold; releasing peers with `DBG_REPLY_LATER` is not required. The capture thread must own continuation. See [ResumeThread remarks](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-resumethread) and [ContinueDebugEvent](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-continuedebugevent). The hold loop must check both deadlines itself; the current outer debug-loop deadline would not run while a new inner wait blocks.

## Required current inputs and independent native result

Reuse `buildNativeFrameManifest`'s actual phase4/participant/arena/shape/physical-list/geometry checks and full-body capture. Required live fields include selected body+34 position,+40 momenta,+4c angular momenta,+58 quaternion,+68 velocity,+74 force,+80 torque,+9c inertia,+a8/+ac mass/inverse mass,+c4/+e4 derived matrices,+108..128 flags/time/cache/state,+140 shapes,+148 callback,+154..15e candidate ownership/counts, and full vehicle wheel/contact/drive/control state. Current geometry/resource bytes, runtime-pack roots, spatial registration, numerical context and reached model/effect/audio descendants are inputs too. Old model indices, coordinates, force preimages or heap addresses cannot seed them.

The existing preflight CLI deliberately requires a completed original before/after baseline and independently checks candidate bytes against native after output. A held pre-input has no native counterfactual after. A new planner must therefore label its unmodified run **source-only counterfactual planning**, rather than bypassing that CLI's validation or claiming an unobserved baseline match. The eventual controlled native output can still be compared honestly against the independently captured post-input entry.

For the positive collision claim, require kind1, the selected actual type3 participant, matching current terrain type6/7 plane/cell/normal, actual104-byte dispatcher data and caller/EDX delta proof. Retain the current candidate arena at dispatcher time (root91e788, fixed0x8000-byte pool), because a later frame can overwrite candidate rows. Dispatcher ESP must equal frame entry ESP−28 and its return must be relocated474ada. Compare actual ordered events and complete frame state separately, including exact geometry/mutable descendants, with no output exclusions introduced to obtain a match. A source forecast, horizontal normal, camera type4 contact, later initialized state or partially executed replay is insufficient.

If the new geometry is too far from a border or any reached dependency is unavailable, retain the miss/unbound reason and decline the input. This proposed force-only experiment would establish one controlled chassis-border response if it succeeds; natural wall driving, ceilings and sustained inverted handling would remain separate missing scenarios.
